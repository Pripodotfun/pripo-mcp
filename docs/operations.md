# Operations and recovery

The configured factory must reference the configured vault and be a registered registrar. Startup and tool calls check chain identity. Market tools validate factory registration through the pinned SDK. Deployment JSON is trusted local configuration: wiring checks do not attest deployed bytecode against source. Keep RPC credentials, operator keys and state files outside Git.

The transaction journal binds chain, factory, vault, owner and signer. Startup verifies signed-transaction hashes, recovered signer, chain and nonce before accepting requests. One process owns the journal lock, and only one unresolved transaction is accepted. Atomic writes fsync both the file and its directory before network submission. A storage failure freezes writes for that process; restore durable storage and restart before continuing.

Do not delete a journal to work around pending transactions, nonce errors, parse failures or lock failures. Losing it loses the mapping between business intent IDs and submitted transactions. Maintain a secure backup together with the deployment configuration. Signed transaction bytes are sensitive and remain broadcastable; the tool responses never return them. A heartbeat lock may remain for approximately 30 seconds after an unclean process death; wait for staleness after verifying no signer process remains.

For `submission_unknown`, query `get_transaction_status`, then retry the original mutating tool with the original ID and arguments if needed. A lost send response never causes a replacement transaction. If the mined nonce is already past the journal nonce but a receipt is unavailable, the server waits; it does not assume a successful trade. Pending receipts must reach `confirmations` and match a canonical block before becoming `confirmed` or `reverted`.

A disappeared or noncanonical receipt downgrades a previously completed entry when that entry is queried. Confirmation depth is an operational heuristic, not an absolute finality guarantee. Deep reorgs, conflicting use of the signer, permanently missing receipts and nonce regression require manual reconciliation. There is no automatic fee bump or escape hatch that signs a replacement. Do not run two MCP configurations with the same signer but different journals.

The journal is capped at 10,000 intents and fails closed when full. This release has no automated pruning or compaction. Retain request-ID tombstones and nonce history in any future migration; deleting completed entries weakens replay protection. Backups and recovery procedures must preserve the complete journal. Keep the server local: it has no hosted authentication, tenant isolation, or remote key custody model.

Limits in deployment JSON apply per transaction: `maxGas`, `maxFeePerGas`, `maxNativeValue` (value excluding gas) and `maxCreationSeedBondUsdc`. The operator must cover maximum gas cost plus native value. Creation is opt-in and funded by the operator, separately from owner trading policy. A policy can be revoked or changed while a transaction is pending; a successful simulation is not a promise that execution will succeed.

No tool exposes arbitrary transaction signing, native/token transfers, withdrawals, approvals or owner policy changes. The write tools rebuild and simulate their allowed SDK call just before signing. Unknown RPC failures are reported without upstream URLs or request bodies. Use node/provider monitoring outside the MCP responses for troubleshooting. Market symbols and other chain/indexer content are data, not instructions for an agent.
